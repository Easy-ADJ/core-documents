# ⚙️ Git 컨벤션

## 커밋 메시지

형식은 **`prefix: 작업 내용 요약`**. prefix를 통일해두면 히스토리만 봐도 맥락이 잡힌다.

| prefix | 용도 | 예 |
|---|---|---|
| `feat` | 기능 구현 | `feat: 결제 멱등성 처리 구현` |
| `fix` | 오류 수정 | `fix: 잔액 음수 처리 오류 수정` |
| `refactor` | 코드 개선 | `refactor: 조건문 메서드 분리` |
| `docs` | 문서·주석 | `docs: ERD 문서에 멱등 키 반영` |
| `test` | 테스트 코드 | `test: 분개 기록 단위 테스트 추가` |
| `chore` | 설정 등 기타 | `chore: .gitignore 설정` |

## 커밋 단위

- **하나의 커밋 = 하나의 논리적 변경**
- 기능 구현 → 리팩토링 → 테스트를 각각 별도 커밋으로 분리한다
- "일단 돌아가게 만들고 → 정리하는" 흐름을 커밋으로 그대로 표현한다

```text
feat: LedgerEntry 엔티티 기본 구조 생성
feat: 분개 기록 API 구현
fix: 차변·대변 합계 검증 누락 수정
refactor: 검증 로직 메서드 분리
test: 멱등 키 중복 요청 테스트 추가
```

## 브랜치 플로우

`main` ← `develop` ← `feat/기능명`

| 브랜치 | 용도 |
|---|---|
| `main` | 배포용. **PR로만 병합**하며 중요한 기능은 팀원 합의 하에 |
| `develop` | 기능 개발용 작업 브랜치 |
| `feat/기능명` | 기능별로 잘게 나누고 싶을 때 |

- PR 본문에 이슈 번호를 적는다. (`Closes #12`)
- **계약을 바꾸는 PR은 상대 담당자를 리뷰어로 지정한다.** ([계약 변경 절차](../02-design/service-contracts.md#3-계약-변경-절차))
