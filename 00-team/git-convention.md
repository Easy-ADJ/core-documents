# ⚙️ GitHub 관리 방식

### 📃 예시

1. **커밋 메시지 규칙** : prefix를 통일해두면 히스토리만 봐도 맥락 파악이 수월

	- **`feat`** : 기능 구현 (`feat: 계좌 입출금 기능 구현`)
	- **`fix`** : 오류 수정 (`fix: 잔액 음수 처리 오류 수정`)
	- **`refactor`** : 코드 개선 (`refactor: 조건문 메서드 분리`)
	- **`docs`** : 주석·README 작성 (`docs: README 과제 설명 추가`)
	- **`test`** : 테스트 코드 (`test: 입금 메서드 단위 테스트 추가`)
	- **`chore`** : 설정 파일 등 기타 (`chore: .gitignore 설정`)

---

2. **커밋 메시지 형식** : <u>**`prefix: 작업 내용 요약`**</u>

	```text
	feat: 계좌 입출금 기능 구현
	fix: 잔액 음수 처리 오류 수정
	refactor: 조건문 메서드 분리
	docs: README 과제 설명 추가
	test: 입금 메서드 단위 테스트 추가
	chore: .gitignore 설정
	```

---

3. **커밋 단위 기준**

	- 하나의 커밋 = 하나의 논리적 변경
	- 기능 구현 → 리팩토링 → 테스트를 각각 별도 커밋으로 분리
	- "일단 돌아가게 만들고 → 정리하는" 흐름을 커밋으로 그대로 표현

---

4. **브랜치 플로우**

	- **`main`** : 최종 제출본이자 배포용. 시스템 개발 담당자 판단 하 혹은 중요한 기능이 포함된 경우 팀원 합의 하에 PR로 병합
	- **`develop`** : 기능 개발용 작업 브랜치. 개발 완료 후 `main`으로 PR 병합
	- **`feat/기능명`** : 기능 별로 잘게 나누고 싶을 때 추가

---

5. **README 작성** : 동료 평가자가 가장 먼저 보는 파일

	- 과제 요구사항 요약
	- 구현한 기능 목록
	- 실행 방법
	- 고민했던 부분이나 개선 여지 간단히 기록

---

6. **실제 커밋 흐름 예시**

	```text
	feat: BankAccount 클래스 기본 구조 생성
	feat: 입금(deposit) 메서드 구현
	feat: 출금(withdraw) 메서드 구현
	fix: 잔액 부족 시 예외 처리 누락 수정
	refactor: validate 메서드 분리
	docs: README 과제 설명 및 실행 방법 추가
	```
