# 🏗️ 시스템 아키텍처

> **이 문서가 현행 아키텍처의 단일 출처(single source of truth)다.**
> [확정 기획서](../01-planning/service-spec.md)의 §4.1 구성도·§4.3 기술 선택 표는 단일 서버 + Amazon RDS를 전제로 쓰였으므로 현행이 아니다. 아키텍처에 관해 두 문서가 다르면 **이 문서가 맞다.**

---

## 1. 전체 구성

```
        [클라이언트: 승객 앱 / 관리자 콘솔]
                      │  REST (Idempotency-Key 헤더)
                      ▼
   ┌──────────────────────────────────────────────┐
   │  결제 서버          원장 서버        정산 서버  │
   │  (payment)   ──▶   (ledger)   ◀──  (settlement)│
   │  김주엽             이치헌            허진수     │
   └──────────────────────────────────────────────┘
                      │  JDBC
                      ▼
        [Supabase PostgreSQL] ← 인스턴스 1개를 3개 서비스가 공유
           payment  : trips, payments
           ledger   : ledger_accounts, ledger_entries
           settlement: settlement_batches, settlement_items
```

| 서비스 | 담당자 | 책임 | 레포 |
|---|---|---|---|
| 결제 (payment) | 김주엽 | 운행 종료 시 결제 청구, 멱등 처리, 취소/환불 | 🚧 미생성 |
| 원장 (ledger) | 이치헌 | 이중기입 분개 기록, 잔액 계산, 정합성 검증 | 🚧 미생성 |
| 정산 (settlement) | 허진수 | 일 단위 집계 배치, 정산 내역서, 대사 | 🚧 미생성 |

- 서비스 간 통신은 **동기 REST 호출**. 호출 관계와 계약은 [service-contracts.md](./service-contracts.md) 참조.
- 서버 간 호출 대상 주소는 **환경변수로 주입**한다(하드코딩 금지). 변수 이름은 [dev-environment.md](../03-development/dev-environment.md) 참조.

## 2. 왜 이렇게 나눴나

**서비스를 3개로 나눈 이유**는 팀원 3명이 서로의 코드를 기다리지 않고 병렬로 개발하기 위해서다. 도메인 경계(결제 / 원장 / 정산)가 [기획서 §3](../01-planning/service-spec.md)의 기능 명세 단위와 그대로 일치해, 담당자별로 책임이 겹치지 않는다.

**DB는 하나로 둔 이유**는 3주 개발 기간에 DB 인스턴스 3개를 각각 셋업·관리할 여유가 없고, Supabase 프로젝트 하나로 스키마·백업·접속을 한 곳에서 관리하는 편이 단순하기 때문이다.

**대신 이 선택은 대가를 치른다.** 아래 3·4절이 그 대가를 다룬다.

---

## 3. 결제와 원장의 원자성

> 🚧 **미확정 — 8/11 회의 안건.** 이 결정이 결제 서버 구현 방식을 좌우한다.

[기획서 §4.4](../01-planning/service-spec.md)는 결제 생성을 이렇게 규정했다.

> `Payment` insert + `LedgerEntry`(차변/대변 2건) insert를 **하나의 DB 트랜잭션**으로 묶어 원자성 보장

서버가 갈린 지금도 **DB가 하나라서 이 방식이 물리적으로는 여전히 가능하다.** 그래서 선택지가 생긴다.

| | (A) 결제 서버가 원장 테이블에 직접 write | (B) 결제 → 원장 API 호출 |
|---|---|---|
| 원자성 | 로컬 트랜잭션으로 보장됨 | HTTP 경계를 넘어 보장 불가 |
| 서비스 경계 | **무너진다** — 원장 스키마를 바꾸면 결제가 깨짐 | 유지됨 |
| 구현 난이도 | 낮음 | 실패 시 보상 로직 필요 |
| 현재 전제와 | 어긋남 | **일치**("서로 API로 호출") |

**(B)를 택할 경우 반드시 함께 정해야 할 것** — 결제는 성공했는데 원장 기록이 실패하면 무엇을 하는가?

1. **재시도**: 결제 서버가 원장 호출을 N회 재시도. 원장 API가 멱등해야 한다(같은 `transactionId`로 두 번 와도 분개 1세트만).
2. **결제 롤백**: 원장 실패 시 결제도 실패 처리. 단순하지만 원장 서버가 잠깐 죽으면 결제가 전부 실패한다.
3. **사후 대사**: 결제는 성공시키고, 원장 기록은 별도 큐/배치로 재시도. 일시적으로 원장에 빠진 건이 생기며, 정산 전 대사 배치가 이를 잡아낸다.

> 어느 쪽을 택하든 **결정과 근거를 이 절에 기록한다.** 기록 없이 코드로만 정해지면 나머지 두 명이 알 수 없다.

## 4. 공유 DB의 함정 — 테이블 직접 접근 ⚠️

DB가 하나이므로 정산 서버는 결제 테이블을 **그냥 조인할 수 있다.** 코드도, DB도 이를 막지 않는다.

한 번 그렇게 시작하면:
- 결제 담당자가 `payments` 컬럼을 바꾸는 순간 정산 배치가 조용히 깨진다
- API 계약을 아무리 잘 써놔도 실제 의존 관계는 문서에 없는 SQL 안에 숨는다
- 서비스를 3개로 나눈 의미가 사라지고, 배포만 3번 하는 모놀리식이 된다

**따라서 다른 서비스가 소유한 테이블에 직접 접근하지 않는다.** 규칙 전문과 예외 처리 절차는 [service-contracts.md](./service-contracts.md#0-테이블-직접-접근-금지)에 있다.

소유권을 DB 권한으로 실제 강제할지(PostgreSQL 스키마 분리)는 [erd.md](./erd.md)의 논점으로 남아 있다.

## 5. 인프라

| 요소 | 선택 | 비고 |
|---|---|---|
| DB | **Supabase PostgreSQL** (인스턴스 1개 공유) | 기획서 §4.3의 Amazon RDS를 대체 |
| 애플리케이션 | Spring Boot 4 / Java 17 | 서비스 3개 각각 독립 실행 |
| 정산 배치 | Spring Batch (정산 서버 내부) | 기획서 §3.3 |
| 배포 위치 | 🚧 미확정 — AWS EC2 3대 vs 1대에 3프로세스 | 비용·시간 고려해 결정 |
| 배치 스케줄링 | 🚧 미확정 — EventBridge vs Spring `@Scheduled` | 서버가 상시 떠 있다면 후자가 단순 |
| 정산 리포트 보관 | 🚧 미확정 — S3 vs Supabase Storage | DB를 Supabase로 옮긴 만큼 Storage도 후보 |

> 가상 스레드(`spring.threads.virtual.enabled=true`)는 기획서 §4.3대로 3개 서비스 모두에 적용한다. 서비스 간 동기 REST 호출이 늘어 I/O 대기가 오히려 많아졌으므로 근거가 더 강해졌다.
