> 🚧 **작성 중** — 아래는 [기획서 §3.2](../../01-planning/service-spec.md)에서 도출한 초안이다. 구현하면서 담당자가 채운다.

## 제공 API

### `POST /api/ledger/entries` — 분개 기록

하나의 거래(Transaction)에 대해 **차변과 대변을 원자적으로 함께** 기록한다. 결제 서버와 정산 서버가 모두 호출한다.

| | |
|---|---|
| 요청 본문 | `transactionId`(같은 거래를 묶는 그룹 키), 분개 목록 `[{accountId, direction, amount}, ...]` |
| 검증 | **차변 합계 = 대변 합계**가 아니면 `400` 거부 |
| 멱등성 | 같은 `transactionId`로 재요청이 오면 **재기록하지 않고 기존 결과를 반환** (`transaction_id` UNIQUE 제약) |
| 응답 | `201 Created` — `transactionId`, 생성된 분개 목록 |

- 결제 승인: 차변(플랫폼 예수금 증가) + 대변(기사 미지급금 증가)
- 결제 취소: 위의 **역방향 분개를 추가**한다. 원본을 수정·삭제하지 않는다(append-only)

### `GET /api/ledger/accounts/{accountId}/balance` — 잔액 조회

계정의 현재 잔액을 **분개의 합으로 계산해** 반환한다. 잔액 컬럼을 따로 두고 갱신하지 않는다 — 그래야 이상이 생겼을 때 분개 이력을 replay해 추적할 수 있다.

- 🚧 특정 시점 기준 잔액(`asOf` 파라미터)이 필요한지 — 정산 대사에서 "전일 자정 기준"이 필요할 수 있다
- 🚧 건수가 늘면 매번 전체 SUM이 느려진다. 스냅샷 도입 여부는 성능 측정 후 결정

### `GET /api/ledger/accounts?ownerType=&ownerId=` — 계정 조회

`accountId`를 모르는 호출자가 기사/플랫폼 기준으로 계정을 찾는다. 🚧 계정 생성 시점(기사 등록 시 vs 첫 거래 시)도 함께 정해야 한다.

### 정합성 검증

특정 거래 또는 기간의 **모든 분개 합이 정확히 0인지** 검증한다. 합이 0이 아니면 정합성 이상.

- 🚧 API로 노출할지(`GET /api/ledger/verify?from=&to=`), 배치로만 돌릴지, 둘 다일지
- 🚧 이상 발견 시 알림 방식 — 로그 / 응답 코드 / 관리자 대시보드 배지

## 다른 서버에 대한 의존

**없다.** 원장은 아무도 호출하지 않고 호출만 받는다. 그래서 **가장 안정적으로 유지해야 하는 서버**이며, 개발 순서상 먼저 API가 확정돼야 나머지 둘이 진행된다.

## 미확정 항목

- [ ] 차변 합 = 대변 합 검증을 DB 제약으로 강제할지, 애플리케이션에서 할지
- [ ] `transactionId`를 호출자가 생성할지, 원장이 발급할지 — 멱등성을 위해 **호출자 생성**이 유리
- [ ] 계정 종류 확장 (기획서 §3.5의 포인트 결제 대비)
- [ ] 잔액 조회 성능 — 분개가 쌓였을 때의 응답 시간
- [ ] 정합성 검증 결과를 어디에 남길지
