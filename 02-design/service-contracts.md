# 🤝 서비스 간 계약

> 서버 3개가 서로를 어떻게 부르는지, 무엇을 하면 안 되는지를 정한다.
> 이 문서는 팀 공동 소유다. 혼자 고치지 말고 3절 절차를 따른다.

---

## 0. 테이블 직접 접근 금지

**다른 서비스가 소유한 테이블을 직접 SELECT / JOIN / INSERT / UPDATE 하지 않는다.** 반드시 소유 서비스의 API를 경유한다.

| 하면 안 되는 것 | 대신 |
|---|---|
| 정산이 `PAYMENT`를 직접 조회 | 결제 `GET /api/payments?date=` |
| 결제가 `LEDGER_ENTRIES`에 직접 insert | 원장 `POST /api/ledger/entries` |
| 정산이 `LEDGER_ENTRIES`를 SUM | 원장 `GET /api/ledger?driver_id=` |

DB 인스턴스가 서비스마다 하나씩 있으므로 **남의 업무 테이블에는 접속 자체가 불가능하다.** 위 표는 지키려고 노력할 규칙이 아니라 이미 강제된 사실이다. 그래서 남의 DB 접속 정보는 요청하지도 공유하지도 않는다 — 이 경계를 우회하는 유일한 방법이기 때문이다.

### ⚠️ 예외는 로그인 DB 하나뿐

`MANAGER_ACCOUNTS`·`DRIVER_ACCOUNTS`에는 세 서버와 대시보드가 모두 직접 접속한다. 기사 이름·계좌번호가 앞단에 서버 없이 공유되는 참조 데이터이기 때문이다. ([사유](./architecture.md#2-왜-이렇게-나눴나))

| 항목 | 로그인 DB에서만 다른 점 |
|---|---|
| 접근 방법 | API가 아니라 JDBC 직접 SELECT |
| 결합점 | API 계약이 아니라 테이블 스키마 |
| 스키마 변경 영향 | 세 서버 쿼리가 즉시 깨진다 |
| 변경 절차 | `schema` 이슈에 **세 명 전원 멘션** |

- JOIN과 FK는 여전히 불가능하다. 접속이 열린 것과 같은 DB가 된 것은 다르다.
- 세 서버는 읽기 전용 계정(`payment_ro`·`ledger_ro`·`settlement_ro`)을 쓴다. write는 대시보드(회원가입)만 한다.
- ⛔ 이 예외를 다른 서비스의 업무 테이블로 확대 해석하지 않는다.

### 대신 계약이 결합점이 된다

경계가 테이블에서 API로 옮겨갔을 뿐, 의존은 사라지지 않았다.

1. 정산이 결제 API 응답의 `amount` 필드를 읽는다.
2. 결제 담당자가 그 필드 이름을 바꾼다.
3. 정산이 조용히 틀린 금액을 뱉는다 — **아무도 컴파일 에러를 못 본다.**

그래서 3절의 계약 변경 절차가 이 문서에서 가장 중요하다.

## 1. 호출 관계

| # | 호출자 | 피호출자 | 엔드포인트 | 목적 | 실패 시 |
|---|---|---|---|---|---|
| 1 | 결제 | 원장 | `POST /api/ledger/entries` | 결제 승인 분개 | 2회 재시도 후 **결제도 실패** |
| 2 | 결제 | 원장 | `POST /api/ledger/entries` | 결제 취소 상쇄 분개 | 위와 동일 |
| 3 | 정산 | 원장 | `GET /api/ledger/unpaid?date=` | 배치 대상 선별 | 2회 재시도 후 Job 실패 |
| 4 | 정산 | 원장 | `GET /api/ledger?driver_id=` | 금액·근거 조회 | 위와 동일 |
| 5 | 정산 | 원장 | `POST /api/ledger/entries` | 정산 확정 지급 분개 | 위와 동일 |
| 6 | 정산 | 결제 | `GET /api/payments?date=` | 대사 교차검증 | 정산 `CONFIRMED` 보류 |

의존 방향은 **결제 → 원장, 정산 → (원장, 결제)** 다. 호출은 전부 동기 REST.
**원장은 아무도 호출하지 않는다.** 그래서 원장 API 변경의 파급이 가장 크고, 가장 먼저 확정돼야 한다.

> ⚠️ 3번과 4번은 **원장이 새로 구현해야 하는 API**다. 응답 형태를 정산 담당자와 먼저 맞춰야 한다.

### 클라이언트 → 서버

| 클라이언트 | 피호출자 | 인증 |
|---|---|---|
| 승객 앱 | 결제 서버 | `Idempotency-Key` 헤더 |
| 기사·관리자 대시보드 | 원장 서버 | `Bearer Token` |

- 대시보드는 로그인 DB에도 직접 접속한다. 클라이언트가 서버를 경유하지 않는 유일한 경로다.
- **대시보드는 정산 서버를 호출하지 않는다.** 필요해지면 그때 연결한다.

## 2. 공통 규약

| 항목 | 규약 |
|---|---|
| 멱등성 | 쓰기 호출은 `Idempotency-Key` 헤더를 전파한다. 같은 키로 오면 **재실행 없이 첫 결과를 반환** |
| 원장 분개 멱등 | `LEDGER_ENTRIES.idempotency_key`에 UNIQUE. 같은 키로 두 번 와도 분개가 1세트만 생긴다 |
| 타임아웃 | 연결 5초 / 응답 10초 |
| 재시도 | 5xx·타임아웃만 최대 2회, 지수 백오프. **4xx는 재시도하지 않는다** |
| 금액 타입 | `BigDecimal`, 원화 정수. JSON에서는 **문자열**로 주고받아 부동소수점 손실을 막는다 |
| 날짜·시각 | 날짜 `yyyy-MM-dd`, 시각 ISO-8601 UTC |

에러 응답은 아래 형식으로 통일한다.

```json
{
  "code": "LEDGER_ENTRY_UNBALANCED",
  "message": "차변 합계와 대변 합계가 일치하지 않습니다",
  "transactionId": "..."
}
```

- HTTP 상태코드로 종류를 구분하고(400 요청 오류 / 404 없음 / 409 충돌 / 500 서버 오류), `code`로 원인을 특정한다.
- 호출자는 **`code`로만 분기한다.** `message`는 로그에만 쓴다.

> 타임아웃이 3초/5초보다 넉넉한 이유는 Railway가 유휴 시 인스턴스를 재우기 때문이다. 짧게 잡으면 데모 첫 시도가 타임아웃으로 죽는다.

## 3. 계약 변경 절차

API 시그니처·필드·에러 코드를 바꾸려면 **코드보다 문서와 이슈가 먼저다.**

1. **제공자 레포에 이슈를 연다** (라벨 `contract`) — 무엇을 왜 바꾸는지, 변경 전/후를 나란히 적는다.
2. **소비자 담당자를 멘션한다** — 1절 표에서 그 API를 호출하는 사람을 찾는다.
3. **합의 후 이 문서와 [services/](./services/) 파일을 갱신한다.**
4. **그다음 구현한다.**

> ❌ 코드를 먼저 바꾸고 문서를 나중에 맞추는 것은 금지.
> 상대는 문서를 보고 개발 중이므로, 문서가 늦으면 그만큼 상대가 틀린 코드를 쓴다.

DB 스키마 변경도 같은 절차를 따른다(라벨 `schema`). DB는 나뉘었지만 스키마 변경은 그 테이블을 노출하는 API 응답을 바꾸므로 상대에게 영향이 간다.
