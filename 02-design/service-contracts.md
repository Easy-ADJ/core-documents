# 🤝 서비스 간 계약

> 서버 3개가 서로를 어떻게 부르는지, 그리고 **무엇을 하면 안 되는지**를 규정한다.
> 이 문서는 **팀 공동 소유**다. 혼자 고치지 말고 3절의 변경 절차를 따른다.
> 각 서버가 제공하는 API의 상세 스펙은 [services/](./services/) 아래 담당자별 문서에 있다.

---

## 0. 테이블 직접 접근 금지

**다른 서비스가 소유한 테이블을 직접 SELECT / JOIN / INSERT / UPDATE 하지 않는다. 반드시 소유 서비스의 API를 경유한다.**

| 하면 안 되는 것 | 대신 |
|---|---|
| 정산 서버가 `payments`를 직접 조회 | 결제 서버 `GET /api/payments?date=` 호출 |
| 결제 서버가 `ledger_entries`에 직접 insert | 원장 서버 `POST /api/ledger/entries` 호출 |
| 정산 서버가 `ledger_entries`를 SUM해서 잔액 계산 | 원장 서버 `GET /api/ledger/accounts/{id}/balance` 호출 |

### 왜 규칙으로만 지켜지나

DB가 [Supabase PostgreSQL 인스턴스 하나](./architecture.md#1-전체-구성)라서 **기술적으로는 아무나 아무 테이블에나 접근할 수 있다.** 컴파일러도 DB도 이를 막지 않는다. 이 경계는 오직 이 규칙으로만 존재한다.

지키지 않으면 이렇게 된다.

1. 정산 배치가 `payments`를 직접 조인한다 (당장은 편하다)
2. 결제 담당자가 `payments.status` 값 하나를 추가한다
3. 정산 배치가 조용히 틀린 금액을 뱉는다 — **아무도 컴파일 에러를 못 본다**
4. 원인을 찾으려 해도, 정산이 결제에 의존한다는 사실이 문서 어디에도 없다

### 예외를 두려면

정말 API로 감당이 안 되는 경우(예: 정산 배치가 수만 건을 페이지네이션으로 가져오는 게 비현실적)라면 **이 문서에 예외를 명시적으로 기록한다.** 기록할 것:

- 어느 서비스가 어느 테이블을 읽는지
- 왜 API로는 안 되는지
- 해당 테이블 스키마 변경 시 누구에게 알려야 하는지

말로 합의하고 코드에만 남기는 것을 금지한다.

## 1. 호출 관계

> 🚧 아래는 [기획서 §3](../01-planning/service-spec.md)에서 도출한 **초안**이다. 각 서버 API가 확정되면 담당자가 [services/](./services/)를 갱신하고, 그 결과를 이 표에 반영한다.

| # | 호출자 | 피호출자 | 목적 | 엔드포인트(안) | 방식 | 실패 시 |
|---|---|---|---|---|---|---|
| 1 | 결제 | 원장 | 결제 승인 시 차변/대변 분개 기록 | `POST /api/ledger/entries` | 동기 | 🚧 [architecture.md §3](./architecture.md#3-결제와-원장의-원자성) 결정에 따름 |
| 2 | 결제 | 원장 | 결제 취소 시 상쇄(역방향) 분개 기록 | `POST /api/ledger/entries` | 동기 | 위와 동일 |
| 3 | 정산 | 결제 | 전일 완료 결제 내역 조회 (배치 Reader) | `GET /api/payments?date=` | 동기 | 배치 실패 처리, 재실행 |
| 4 | 정산 | 원장 | 기사 미지급금 잔액 조회 (대사 검증) | `GET /api/ledger/accounts/{accountId}/balance` | 동기 | 대사 불가 → 정산 CONFIRMED 보류 |
| 5 | 정산 | 원장 | 정산 확정 시 지급 분개 기록 | `POST /api/ledger/entries` | 동기 | 🚧 미확정 |

**의존 방향 요약**: 결제 → 원장, 정산 → (결제, 원장). **원장은 아무도 호출하지 않는다** — 원장을 가장 안정적으로 유지해야 하는 이유이고, 원장 API 변경이 가장 파급이 크다는 뜻이다.

## 2. 공통 규약

> 🚧 아래 값들은 **제안**이다. 8/11 회의에서 확정한다.

| 항목 | 규약 |
|---|---|
| 멱등성 | 쓰기 성격의 서버 간 호출은 `Idempotency-Key` 헤더를 전파한다. 같은 키로 재요청이 오면 피호출 서버는 **재실행하지 않고 첫 결과를 반환**한다 |
| 원장 분개 멱등 | 원장은 `transactionId`(같은 거래를 묶는 그룹 키)에 UNIQUE 제약을 걸어, 같은 거래로 두 번 와도 분개가 1세트만 생기게 한다 |
| 타임아웃 | 연결 3초 / 응답 5초 |
| 재시도 | 5xx·타임아웃만 최대 2회, 지수 백오프. **4xx는 재시도하지 않는다**(요청 자체가 틀린 것) |
| 금액 타입 | `BigDecimal`, 원화 정수(소수점 없음). JSON에서는 **숫자가 아닌 문자열**로 주고받아 부동소수점 손실을 막는다 |
| 날짜/시각 | 날짜는 `yyyy-MM-dd`, 시각은 ISO-8601 UTC (`2026-08-11T00:00:00Z`) |
| 에러 응답 | 아래 공통 포맷 |

```json
{
  "code": "LEDGER_ENTRY_UNBALANCED",
  "message": "차변 합계와 대변 합계가 일치하지 않습니다",
  "transactionId": "..."
}
```

- HTTP 상태코드로 종류를 구분하고(400 요청 오류 / 404 없음 / 409 충돌·중복 / 500 서버 오류), `code`로 원인을 특정한다.
- 호출자는 `message`를 로그에만 쓰고 **분기 조건으로 삼지 않는다**. 분기는 `code`로 한다.

## 3. 계약 변경 절차

API 시그니처·필드·에러 코드를 바꾸려면 **코드보다 이 문서와 이슈가 먼저다.**

1. **제공자 레포에 이슈를 연다** — 라벨 `contract`. 무엇을 왜 바꾸는지, 기존 호출자가 무엇을 고쳐야 하는지 적는다
2. **소비자 담당자를 멘션한다** — 1절 표에서 그 API를 호출하는 사람을 찾는다
3. **합의 후 이 문서와 [services/](./services/) 해당 파일을 갱신한다**
4. **그다음 구현한다**

> ❌ **금지**: 코드를 먼저 바꾸고 문서를 나중에 맞추기. 상대 서버는 문서를 보고 개발 중이므로, 문서가 늦으면 그 시간만큼 상대가 틀린 코드를 쓴다.

DB 스키마 변경도 같은 절차를 따른다 — 라벨 `schema`, 담당자 2명 모두 멘션. 자세한 규칙은 [github-workflow.md](../00-team/github-workflow.md) 참조.
