## 1. 문제 → 프로젝트 매핑 (팀 선택용 후보 5~6개)

- 각 후보는 **Java / Spring Boot 4 / AWS** 스택으로 3~4주 내 완주 가능하도록 범위를 좁혀 정리했다. 팀 회의에서 이 중 하나를 선택하거나 조합해 확정하면 된다.

### 후보 A. 실시간 차량 위치 관제 대시보드 *([문제 1](./mobility-backend-problems.md#문제-1-대규모-동시-위치-업데이트-처리-실시간-위치-추적) 대응)*

- **시나리오**: 여러 대의 차량(시뮬레이터로 위치를 계속 전송)의 현재 위치를 관제 대시보드에서 실시간으로 확인하고, 반경 내 차량을 조회한다.
- **핵심 기능**: 위치 업데이트 수신 API, WebSocket/STOMP 기반 실시간 브로드캐스트, 반경 검색(주변 차량 찾기), 이동 경로 히스토리 조회
- **아키텍처**: Spring Boot 4(WebSocket, 가상 스레드로 대량 동시 연결 처리) + **Amazon ElastiCache(Redis) Geospatial 인덱스**로 좌표 저장·반경 질의 + RDS(이력 저장)
- **난이도**: ★★☆ (중) — WebSocket과 Redis Geo 학습이 필요하지만 외부 프로토콜 연동이 없어 가장 손에 잡히는 구현
- **3~4주 로드맵**: 1주차 위치 업데이트 REST API + Redis Geo 저장 → 2주차 WebSocket 실시간 푸시 + 반경 검색 API → 3주차 대시보드 연동 + 부하 시뮬레이터(가짜 차량 다건 동시 전송) → 4주차 통합·발표 준비
- **상세 기획**: [candidate-a.md](./candidate-a.md)

### 후보 B. 배차 매칭 서비스 (이중 배정 방지) *([문제 3](./mobility-backend-problems.md#문제-3-배차매칭-시-동시성-제어-이중-배정-방지) 대응)*

- **시나리오**: 승객(또는 화물) 콜 요청 시, 주변 기사 여러 명에게 알림이 가고 가장 먼저 응답한 한 명에게만 배정되는 시스템.
- **핵심 기능**: 콜 생성/조회 API, 기사 응답 처리(선착순 배정), 동시 응답 시 단 하나만 성공시키는 동시성 제어, 배정 상태 전이(대기→배정→진행→완료)
- **아키텍처**: Spring Boot 4 + **분산 락(Redisson + ElastiCache Redis)** 또는 DB 낙관적 락으로 "정확히 한 번만 배정" 보장, 상태 머신 설계
- **난이도**: ★★☆ (중) — 동시성 이슈를 눈으로 재현하고 검증하는 테스트 설계가 관건
- **3~4주 로드맵**: 1주차 콜/기사 도메인 모델 + 기본 API → 2주차 동시 응답 시나리오와 분산 락 적용 → 3주차 상태 전이 및 이력 관리, 동시성 테스트(k6/JMeter) → 4주차 통합·발표 준비
- **상세 기획**: [candidate-b.md](./candidate-b.md)

### 후보 C. IoT 텔레메틱스 수집 파이프라인 *([문제 2](./mobility-backend-problems.md#문제-2-iot-텔레메틱스-데이터-수집-파이프라인의-신뢰성) 대응)*

- **시나리오**: 다수의 차량 단말(시뮬레이터)이 주기적으로 위치·속도·연료(배터리) 데이터를 전송하면, 이를 수집·정제해 저장하고 이상치(GPS 튐)를 걸러낸다.
- **핵심 기능**: 단말 데이터 수신(MQTT 또는 REST), 이상치 필터링 규칙, 원본/정제 데이터 저장, 정제 결과 조회 API
- **아키텍처**: **AWS IoT Core**(MQTT 브로커) → **Amazon Kinesis Data Streams** → Spring Boot 4 컨슈머(정제 로직) → RDS/S3 저장
- **난이도**: ★★★ (상) — AWS IoT Core/Kinesis 등 익숙하지 않은 관리형 서비스 학습 비용이 큼
- **3~4주 로드맵**: 1주차 AWS IoT Core 연동 및 데이터 수신 확인 → 2주차 Kinesis 연동 + Spring Boot 컨슈머 → 3주차 이상치 필터링 로직 + 저장 API → 4주차 통합·발표 준비
- **주의**: 팀 전체가 AWS IoT Core를 처음 접한다면 러닝커브가 가장 큰 후보다. AWS 지원 자원을 적극 활용할 팀에 추천.
- **상세 기획**: [candidate-c.md](./candidate-c.md)

### 후보 D. 모빌리티 정산 서비스 (멱등 결제 + 배치 정산) *([문제 4](./mobility-backend-problems.md#문제-4-결제정산의-멱등성과-정합성) 대응)*

- **시나리오**: 승차/이용 완료 시 결제를 처리하고, 기사(또는 차량 소유자)에게 매일 정산 배치를 통해 수익을 계산해 지급 내역을 생성한다.
- **핵심 기능**: Idempotency-Key 기반 결제 API(중복 요청 방지), 이용 내역-결제 내역 매핑, 일 단위 정산 배치(Spring Batch), 정산 결과 대사(합계 검증)
- **아키텍처**: Spring Boot 4 REST API + **Spring Batch**(정산 배치) + RDS(원장 테이블 설계, 차변/대변 합 0 검증)
- **난이도**: ★★☆ (중) — 외부 인프라 의존도는 낮지만 원장/정합성 설계에 대한 이해가 필요
- **3~4주 로드맵**: 1주차 결제 도메인 모델 + Idempotency-Key API → 2주차 원장 테이블 설계 + 이중기입 검증 → 3주차 Spring Batch 정산 잡 구현 → 4주차 통합·발표 준비
- **상세 기획**: [service-spec.md](../service-spec.md) ← **최종 채택**

### 후보 E. EV 충전기 관제 시스템 (경량 OCPP 스타일) *([문제 5](./mobility-backend-problems.md#문제-5-상태-기반-디바이스충전기차량와의-실시간-프로토콜-동기화) 대응)*

- **시나리오**: 여러 충전기(시뮬레이터)가 서버와 WebSocket으로 연결되어 상태(대기/충전중/고장)를 보고하고, 관리자가 원격으로 충전 시작/정지 명령을 내린다.
- **핵심 기능**: 충전기 상태 보고 프로토콜(OCPP 개념을 단순화), 원격 명령 전송, 연결 끊김 감지 및 재연결 시 상태 재동기화
- **아키텍처**: Spring Boot 4 WebSocket 서버 + 상태 머신 + RDS(충전기 상태/이력)
- **난이도**: ★★★ (상) — 프로토콜을 직접 설계해야 하고 연결 끊김·재동기화 같은 예외 시나리오가 많음
- **3~4주 로드맵**: 1주차 WebSocket 연결 관리 + 상태 보고 프로토콜 설계 → 2주차 원격 명령(시작/정지) → 3주차 재연결/재동기화 처리 → 4주차 통합·발표 준비
- **상세 기획**: [candidate-e.md](./candidate-e.md)

### 후보 F. 실시간 이벤트 알림 시스템 *([문제 6](./mobility-backend-problems.md#문제-6-대용량-이벤트-기반-알림상태-전파) 대응, 다른 후보와 결합 가능)*

- **시나리오**: 배차 완료, 도착, 결제 완료 같은 이벤트를 승객/기사 여러 클라이언트에 실시간으로, 서버 재시작에도 유실 없이 전달한다.
- **핵심 기능**: 이벤트 발행 API, 메시지 큐 기반 이벤트 버스, WebSocket/SSE 구독, 재연결 시 유실 이벤트 재전송
- **아키텍처**: Spring Boot 4 + **Amazon SQS/SNS**(이벤트 버스) + WebSocket/SSE 구독 서버
- **난이도**: ★★☆ (중) — 단독 프로젝트보다는 후보 A/B/D의 부가 기능으로 결합하는 것을 권장
- **비고**: 독립 프로젝트로 채택하기보다, 다른 후보의 "3주차 확장 기능"으로 붙이면 완성도를 높이기 좋다.
- **상세 기획**: [candidate-f.md](./candidate-f.md)

## 2. 후보 비교 요약

| 후보 | 핵심 문제 | 난이도 | AWS 활용도 | 3~4주 완주 가능성 | 비고 |
|---|---|---|---|---|---|
| A. 실시간 위치 관제 | 위치 추적 | 중 | 중 (ElastiCache) | 높음 | 가장 무난한 시작점 |
| B. 배차 매칭 | 동시성 제어 | 중 | 중 (ElastiCache/분산락) | 높음 | 백엔드 개념 학습 밀도가 가장 높음 |
| C. IoT 텔레메틱스 | 데이터 파이프라인 | 상 | 높음 (IoT Core+Kinesis) | 보통 | AWS 신규 서비스 학습 비용 큼 |
| D. 정산 서비스 | 결제 정합성 | 중 | 낮음 | 높음 | 인프라 의존 적어 안정적 |
| E. 충전기 관제 | 상태 동기화 | 상 | 낮음 | 낮음~보통 | 프로토콜 직접 설계 부담 큼 |
| F. 이벤트 알림 | 이벤트 전파 | 중 | 중 (SQS/SNS) | - | 단독보다 결합 추천 |

> **추천**
> - 9주 과정 중 실제 개발 기간이 3~4주로 짧은 점을 고려하면, 
> - **후보 A(실시간 위치 관제) 또는 B(배차 매칭)**를 메인으로 삼고, 
> - **후보 F(이벤트 알림)**를 확장 기능으로 결합하는 조합이 완성도와 학습 효과의 균형이 가장 좋다. 
> - AWS 활용을 더 적극적으로 어필하고 싶고 팀의 학습 속도에 자신이 있다면 후보 C를 도전해볼 수 있다.
